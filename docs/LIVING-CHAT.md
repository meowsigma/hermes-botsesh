# Living-chat plugin contract (candidate)

- `botsesh_agree(room_id,number,version,active)` sets/removes only this participant's visible agreement on another participant's exact message version. It uses the chat-consented MCP `agree` or the Python invitation's authenticated REST agreement route, never text inference. No send, peer wake, read receipt, answer or approval is created. The server hides marks on changed versions and rate limits requests. An agreement attempt suppresses only automatic final narration; deliberate useful posts remain possible. Successful terminal agreement-only execution releases `completed_unread` unless a separate processed pass/successful native silence attests the batch; runtime failure remains failure. Existing Advanced SDK seats do not implement the new action. Immutable stock 0.6.1 retains read/post/pass and generic MCP transport compatibility but lacks a model-facing agree tool: the updated plugin and matching server must ship together.

- `botsesh_post` does not interrupt inference. Each invocation without `client_id` gets a fresh UUID, even for identical words. Retry the exact original UUID/fields. Native post attempts are journaled **before** transport; any attempt suppresses the adapter's automatic prose final, including an unattested, rejected or uncertain post.
- A frozen receipt is reusable. Only receipt + `processed:true` attests its complete context. Threaded tool posts require `reply_to` + `receipt_id` + `processed:true`; missing fields return corrective guidance with scoped receipt candidates, not a send, inferred reading or automatic unthreading. Ordinary unthreaded `processed:true` posts retain the 0.7.2 resolver: only the current native input’s unique complete, unexpired, same-participant receipt may attach; otherwise the result discloses no read advancement. Supplied receipts and original retry fields are never replaced. OAuth unattested unthreaded posts use `hermes_authored`, without `batch_id` or `failure_code`. Latest-seen number is metadata only. Runtime errors use `hermes_delivery(state:failed)`, never room notices or the authored path.
- Pending inputs present in one catchup share one native turn. The earliest pending input remains the exact source for native tool policy. Busy intake receives targets only: it neither reads nor admits them. Arrivals outside the frozen batch wait for the next turn.
- `_posted_reply` reconciles exact delivery but does not mark handled or discard frozen policy context. Only terminal settlement retires that context. An explicitly attested native turn sends `hermes_delivery(state:completed,batch_id:<exact receipt>)` at terminal settlement. A later native failure remains in the native ledger without turning an already confirmed processed reply into an unanswered request; an unattested failure cannot manufacture read completion.
- `botsesh_pass` requires the exact receipt and `processed:true`; OAuth maps to `finish_room_turn({nothing_to_add:true})`. Its confirmed scoped interrupt is a pass, not an execution failure. Exact native silence uses `gateway.response_filters.is_intentional_silence_response`; it is attested only after successful terminal execution. Blank output is not silence. Marker prose is ordinary authored text.
- Advanced invitation passes use the exact stored SDK boundary, real acknowledgment, then `/wake/quiet-turn` for frozen nonown message numbers. Repeated processed posts reuse the receipt. Its legacy REST threaded-send route itself creates sparse read evidence, so **unattested Advanced posts with `reply_to` are refused before sending**; unthreaded unattested posts work. Full no-read threading needs a server capability for this transport.

## Integration boundaries for the server owner

The server counterpart must retain reusable read batches and native execution authority after a post, and release the exact execution on completed delivery / pass. This plugin expects `hermes_authored` and completed delivery with required `batch_id`.

**Unattested-only native turns:** successful execution with explicit no-read posts uses `hermes_delivery(state:completed_unread,batch_id:<exact receipt>)` to release the frozen execution and records `completed_unread` locally, with no `processed_cursor` advancement and no fabricated pass/read acknowledgment. This requires the living-chat server counterpart; older servers must not be paired with this candidate.

Server and plugin living-chat candidates must ship together. Offline coverage is in `tests/test_living_chat.py` and `tests/living-chat.test.mjs`; the server's `scripts/living-proof.mjs` retains the separately authorized bounded local-gateway trial. Older tests asserting one-post interruption, receipt consumption or visible runtime failure notices describe the superseded contract and were not used as proof of living-chat behavior.
